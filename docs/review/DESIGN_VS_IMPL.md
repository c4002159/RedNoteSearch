# 设计稿与实现对照（B，第一轮）

**方法与范围（如实）**：在云端用 `main@3830efa` 起前后端（PostgreSQL 16 + pgvector，`python -m app.seed --fake-embeddings` 灌演示数据，超级用户登录），用 Chromium 打开已合并的页面。**视觉上逐像素对照的只有“品牌与切换”和登录页**；其余页面只核对了文字、结构和状态（页面可见文字、是否有禁用措辞）。**没有走生成流程**（没有模型密钥，不调用真实模型），所以任务、版本、结果页、证据与风险提示的真实内容、规则列表有数据时的样子、评测运行指标，都**没有验证**。下表是现象，不是定论；“谁该改”是我的判断。

## 第二轮（2026-11-01）：并排视觉对照（浅色主题）
对照了商品管理、品牌档案、资料列表与上传三页（设计稿图 1 与真实页面并排）。
- **默认主题的原因已查到**：`frontend/src/main.tsx` 里 `<ThemeProvider defaultTheme="dark" …>`，改成浅色（或 `system`）即可；归 A（应用壳）。
- **商品管理**：设计是表格（商品名称、产品线、类目、卖点、状态、操作）加右侧编辑抽屉，实现是卡片行（名称、系列·类目·状态、“有来源 / 总条数”）加“查看、编辑、归档”按钮；字段与契约一致，没有“商品编码”等契约外字段。**③ 视觉差异**；“查看”按钮是设计里没有的（我的 spec 对编辑者只读视图写了“未画”）。
- **品牌档案**：设计是版本列表加带标签的详情，实现是版本卡加纯列表详情；字段一致，没有“创建人”（符合订正）；样例是纯文本。**③**。
- **资料列表与上传**：设计有“版本”单独一列，实现把“v1 · 当前版本”写在标题下；设计的侧栏“待审队列”带数量徽标，实现没有（待审为 0 时可能本就不显示，未验证）；实现多了页头的“待审队列 (0)”按钮。**③**，徽标是否显示请 A 确认。
- **仍没有逐页视觉对照**：用户设置、合规规则、爆款结构分析（评测页见第三轮）（演示数据里没有规则和样本，列表是空状态，只核了文字）。

**③ 无关紧要的视觉差异**

- 设计图的导航里“风险提示规则”画成了“合规规则”；知识库类型里“风险提示制度”画成了“合规制度”。实现用的是“风险提示…”，符合措辞规则，**设计要改**。

**③ 无关紧要的视觉差异**

- 知识库详情：有资料 id、版本组、原文件名、提交人的元数据，分块预览，版本链，审核记录（“管理员直接入库”，原因“—”），符合 spec；“重建索引”“停用”“上传新版本”三个管理员操作都在。

**已核对没有问题**：知识库页头说明与 spec 一致（只有已入库、可检索的当前版本才用于生成和核对）；状态标签“已入库”“可检索”；资料类型有 6 个；爆款分析页写明“添加后不能编辑或删除”“最多 5000 个 Unicode 码点”；添加窗口有三个字段及字数计数（5000、1000、2000），来源链接标“纯文本”；添加成功后进入样本详情；分析窗口写明“20–90 秒、不提供取消、不显示推测进度”；可见文字里没有“合规通过”“已验证事实”“法务批准”“保证合规”。

**这轮没验证（需要真实数据或模型）**：编辑者视角（提交待审、不渲染待审队列与分块预览）；待审队列有数据时与审核窗口（通过、驳回、空理由校验、503、409）；停用窗口；状态为待审核、已驳回、已停用、索引失败的列表与详情；分析的等待状态、超时提示、422 的三种 reason；结构详情和“转为场景模板”；添加样本时文本为空的校验提示。

## 已核对、没有发现问题的点
- 页面可见文字里没有“合规通过”“已验证事实”“法务批准”“保证合规”。
- 商品列表的“有来源 / 总条数”、品牌档案“版本 v1 生效中”、爆款分析“最多 5000 个 Unicode 码点”、风险提示规则页的“不是法律依据，不代表文字合规”等文案都在。
- 登录页有“账号由平台管理员创建，不提供自助注册”。
- 规则页有下载模板、导出、导入、新建；知识库有待审队列；评测页有四种类型筛选。
