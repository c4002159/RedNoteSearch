## 3. 成绩记录：按哪张做

**主页以 `_5` 为准**（它的“最常用”“最热”都是按场景模板统计，与契约 `GET /brands/{id}/results/summary` 一致）。`_1` 的“最热”是单篇文案排名，契约不是这样（契约是按模板取平均，且少于 3 篇有读数时不排名，显示“数据不足”），**不要照 `_1` 做**。`_6` 只借用它的三种空状态的版式（搜索无结果、待补成绩为空、数据不足）。

### 3.1 必须去掉的元素（图里有，后端没有数据或我们不做）

| 元素 | 出处 | 原因 |
|---|---|---|
| “互动率中位数表现超出行业均值 18%”、“平均 7 天互动率 4.18%” | `_1` `_6` | 没有行业数据，也没有阅读或曝光量，不能算互动率 |
| “阅读/曝光”列、公式“(点赞+收藏+评论)/阅读量” | `_6` | 不收集阅读量；契约的“互动”是点赞+收藏+评论之和 |
| 导出报表、日期范围筛选、按场景筛选、“已追踪完结”页签 | `_1` `_6` | 契约没有这些接口或筛选；列表只支持 `needs_metrics`、`q`、分页 |
| “高频复用爆款结构”卡片 | `_1` | 没有这个数据 |
| 模板编号“#04”“#01”等 | `_5` | 没有；用 `scenario_name` |
| 单篇“发布平台/状态”列、“文案 ID: CNX-…”、“RED-METRIC-2025” | `_6` `_9` | 没有对应字段 |
| “Sentry 采集正常、OpenTelemetry 采样 100%”条 | `_9` | 我们没有接入 |
| “CONFIDENCE_THRESHOLD”“RULESET: STATS_V2…”“观察窗口第 3 天初次复盘、第 7 天锁定” | `_6` | 我们的规则是：发布满 3 天仍没有“发布 3 天之后采集”的读数才算待补，没有第 7 天锁定 |
| 全部“（演示数据）”“演示品牌环境”“演示模式”后缀 | 全部 | 是设计稿的标注，真实界面不显示 |
| State 1/2/3/4/5 切换条、“Part 1/Part 3”标签、“异常与错误状态集”各页签 | `_2` `_6` `_9` | 设计工具的演示控件，不是界面 |
| 屏幕里的英文字段名与编码：`published_at`、`post_url`、`captured_at`、`likes`、`source=manual`、`seeding`/`review`、`INVALID_METRIC_VALUE`、`RESULTS_SERVICE_UNAVAILABLE` | `_3` `_4` `_5` `_9` | 界面文案要中文；后端的错误码只有 `VALIDATION_ERROR`（422）、404、403 等统一的几种，见 `API_CONTRACT.md` 第 1 节 |

### 3.2 与契约对得上、要照做的

- 看板：已确认文案总数 `total_copies`、待补成绩数 `pending_count`；“最常用”取 `most_used`（最多 5 项，每项 `scenario_name` 加篇数，占比用前端按 `total_copies` 算）；“最热”取 `hottest`，`enough_data=false` 时显示“数据不足”和 `min_notes`（3）、`notes_with_metrics`，**不排名**；`approximate=true` 的组标“含近似读数”；页脚固定一句“样本很少，只能说明方向，不能说明哪个模板更好”。
- 表：标题（可改，1–200）、场景模板（`scenario_name`，加场景标签用 `scene` 对应的中文名，自定义类型用创作类型接口的 `name`）、推广对象（`promo_label`）、确认时间、发布时间、帖子网址、最新成绩（`latest_metric`）、待补成绩提示。页签只有“全部”和“待补成绩（数量）”，搜索走 `q`。
- 读数：点赞、收藏、评论各 0 到 10 亿的整数；“近似读数”勾选对应 `approximate`；采集时间可选，不得晚于当前时间 10 分钟；来源手填固定为 `manual`，界面显示“手动登记”。**读数只增不改**：“更新表现”其实是再加一条新读数，按钮文案写“登记新读数”，不要暗示可以修改旧的。
- 发布信息：`published_at`（带时区，不得晚于当前时间 10 分钟）、`post_url`（只接受 `https://` 的 `xiaohongshu.com`、`xhslink.com` 及子域，不含账号密码和空白；可清空）。保存短链接 `xhslink.com` 时要提示：“短链接无法自动对上浏览器插件的读数，需要手动登记”。
- 成数字显示：用“万”，不用“w”；有近似标记的读数加“约”。
- 待补成绩的定义（用在提示文字里）：已填发布时间、距发布满 3 天、且没有发布 3 天之后采集的读数。

### 3.3 主页顶部的两个按钮

`_1` 顶部的“登记发布信息”“登记表现数据”没有指定是哪一篇，**不做顶部按钮**，只做每行的操作：没有发布时间或网址时显示“登记发布信息”，有则显示“登记成绩”。这是实现上的决定，B 如有不同意见请在 PR 里回复。

### 3.4 异常（`_9`）按我们的统一做法

列表加载失败用现有的通用错误块（带重新加载与请求编号）；保存失败的 422 在字段下显示 `details.errors` 里的中文提示；403 提示无权限、404 提示不存在，沿用已有页面的写法。不要自造错误码。

## 4. 推广对象（`_7` `_8` `_10`，在 `frontend/src/routes/_layout/generate.tsx`，B 的文件）

- 三个选项：单品、多品组合、活动推广，对应 `promo_type` 的 `product`、`multi_product`、`activity`。
- 单品：商品下拉，选中后下面一行浅色提示。图里是“类目：…·规格 50ml”；真实商品有 `category`、`product_line`，没有规格字段，**只显示这两个**。
- 多品：主推商品必选；搭配商品 1 到 4 个，不可重复、不可含主推；下拉里已选的主推款置灰并标“已设为主推”。**去掉“核心主推款·文案重心占比约 60%”**（没有这个参数），也去掉“随行补香款”“场景延伸款”这类图里编出来的小标签，用 `product_line` 或 `category`。
- 活动：活动名称（1–100，图里写 50）、活动说明（可空，≤1000，图里写 200）、活动福利（≤10 条，每条 ≤200，图里是一个输入框）。**字数上限以契约为准**；福利要能加多条。活动时不选商品。提示一句：“活动文字不经知识库核对，福利里没有资料依据的说法会进入人工逐条确认”。
- 创作场景一排卡片，现在是固定 6 个，**必须改成按品牌的创作类型动态列出**（内置 6 个加品牌自己的），未知类型要有兜底名称。
- 提交校验：组合不合法后端返回 422，前端先拦住（活动名为空、多品没有搭配商品、重复选择）。
- 视觉上 `_10` 的“生成进度”是右下角浮窗，`_7` 是右侧栏；**按现有实现保留右侧栏**，不要改布局。
- 图里顶栏角色文字（“运营”“编辑者”）与现有用户菜单不同，沿用现有的，不改应用壳。

## 5. 创作类型管理（`_11` `_12`）

- 列表：先 6 个内置，再品牌自己的；列“类型名称、类型标识、类型来源、使用模板版本数”，对应 `name`、`key`、`builtin`、`template_count`。**类型标识（key）对用户没有意义**，只在“品牌自定义”行以小号等宽字显示，内置类型显示中文名，不显示 `seeding` 这类英文（图里有，去掉英文）。
- 管理员（品牌 admin）：右上角“新建类型”，自定义行有菜单：重命名、删除；内置行没有操作。编辑者：只读，顶部显示“当前权限：编辑者（只读视图）”。
