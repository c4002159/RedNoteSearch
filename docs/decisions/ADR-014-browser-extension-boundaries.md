# ADR-014 浏览器插件只读已打开页面、只写密钥、不抓取

状态：已实现（PR #164），待 B 用真实 Chrome 实测并在 PR 评论里确认。

## 背景
运营发完笔记后要回系统登记点赞、收藏、评论。手敲容易错。小红书没有给我们开放接口；自动抓取页面有违反平台规则和账号风险，也与“不爬取平台”的既定范围冲突（技术文档 2.1 F13）。

## 决定
1. 插件由我们自己写，运行在用户自己的 Chrome 里；只有用户点开插件并点“读取当前页面”时才运行一次。没有后台脚本、定时任务、翻页，不请求小红书的任何接口，不读评论内容、用户和 Cookie。
2. 读出来的数字由用户核对，点“发送”才发。页面显示“2.1万”这类缩写时标为近似；评论数与页面“共 N 条评论”交叉核对，不一致不放行。
3. 插件用品牌 admin 生成的密钥（`rnk_` 开头）。密钥只在创建时返回一次，库里只存 SHA-256；该密钥**只能调用 `POST /extension/metrics`，不能读任何东西**，用户令牌也不能调这个接口。每品牌最多 10 个有效密钥，可随时作废。
4. 服务端只从网址路径取 24 位笔记 id，丢弃查询串（可能带令牌），不保存网址；只在密钥所属品牌里匹配已保存同一笔记 id 的“已确认文案”。同一篇笔记一小时内最多收 12 条插件读数。
5. 权限只申请 `activeTab`、`scripting`、`storage`；系统地址的访问权限在用户点“保存并授权”时才按所填地址申请。

## 影响与限制
- 选择器依赖桌面版笔记页的结构，页面改版会读不到，此时明确提示读不到什么，用户手填，不猜。
- 密钥存在浏览器本地存储里，未加密；丢失或换电脑就作废重发。
- `xhslink.com` 短链接取不到笔记 id，这类笔记不能自动对上，只能手填。
- 目前生成密钥只有接口，界面等设计稿。密钥页应同时显示“连接配置串”（`rnk1.` + base64url 的 `{s: 地址, k: 密钥}`，含密钥，只显示一次），插件粘贴一次即可配好；后端不参与。
